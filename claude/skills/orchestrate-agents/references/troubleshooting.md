# 返信が来ない時の診断（2026-07-06実例）

1. **bridgeログ確認**: `~/.agents/skills/agmsg/run/<type>-bridge.<team>.<name>.log` を見る。`rc=124`（CLIタイムアウト）+「leaving message unread」なら依頼は未読滞留しており、bridgeプロセス自体も死んでいることが多い
2. **stale pidfile**: bridgeが死んでいるのに `spawn.sh` が「already running (pid N)」と言う場合は、`despawn.sh <team> <from> <name> --force` で登録を掃除してから再spawnする。再spawnしたbridgeは未読メッセージを自動で再処理する
3. **Monitor(watch.sh)が常駐していない場合のfallback**: 返信はDB直読みで取得できる — `sqlite3 ~/.agents/skills/agmsg/db/messages.db "SELECT body FROM messages WHERE team='<team>' AND from_agent='<agent>' ORDER BY id DESC LIMIT 1;"`。到着待ちはバックグラウンドのポーリングループ（10秒間隔でCOUNTを見て、>0で即exit・15分でタイムアウト）にすると、到着時に通知で拾える
4. **CLI更新後は必ずdespawn→再spawn**: bridgeは起動時のCLIバイナリを掴み続けるため、codex CLI等を更新しても既存bridgeには反映されない（実例: 2026-07-10、旧CLIが「gpt-5.6-sol requires a newer version of Codex」の400で全turn失敗し続けた。ログ上はturn completed with errorが並ぶ）。`despawn.sh <team> <from> codex --force` → `ensure-codex.sh` で入れ替える。なお `ensure-codex.sh` は生存確認を兼ねる（生きていれば "already running" のno-op）
5. **既読消化された依頼は再送**: 壊れたbridgeが依頼を既読処理してしまった場合、再spawn後の自動再処理は未読のみが対象なので、該当依頼は `send.sh` で再送する。既読状態は `sqlite3 ~/.agents/skills/agmsg/db/messages.db "SELECT id, read_at IS NOT NULL FROM messages WHERE team='<team>' AND from_agent='claude' ORDER BY id DESC LIMIT 3;"` で確認できる
6. **返信が空body(length 0)で届く送信事故**: Monitor通知が空・DBの `length(body)=0` でも、workerのthreadには作業結果が生きている(bridgeログ末尾に要約が残っていることも多い)。「直前の最終報告がbody空で届いた(送信事故)。全文をそのまま再送して。長文は2〜3分割で送ってよい」と依頼すれば新規調査なしで回収できる(2026-07-18実例: codex-researchの調査報告を3分割再送で全量回収)
7. **turn timeout超過後の沈黙はbridge死亡ではない**: `no turn completion within <N>s; assuming the turn ended and resuming` が出た後にログが静止するのは armed idle（bridge生存・pid健在）。依頼は既読消化済みなので、成果が要るなら再送（項5）か「今すぐ途中経過を送って」での回収、不要なら `despawn --force`（killの成否は必ずpsで検証する）
8. **`watch-once failed with exit 124` の正体**: watch-once.sh 自体の exit code は 0/1/2 のみで、124はbridgeがwatch-onceを実行する app-server `process/spawn`（timeoutMs=timeout+interval+10秒）がkillした時のコード。間欠発生し、3連続でbridgeが自滅して**spawn登録だけがstale残存**する（以後のsendは黙って滞留。despawn --force → ensure-codex で入れ替える）
9. **`codex_models_manager` の `missing field` 系ERRORはハング原因ではない**: brew CLIとChatGPT.app同梱codexのバージョン乖離による models cache（`~/.config/codex/models_cache.json` 共有）のschema非互換で、**fail-open（turnは止まらない）**。恒久対処は `brew upgrade --cask codex` で世代を揃える（更新後は項4のとおり既存bridgeの入れ替えが必要）
10. **sandbox有効セッションでspawnが `sandbox_apply: Operation not permitted` で落ちる**: `excludedCommands`に登録済みでも、呼び出しの形が合わないと除外は効かない。Claude Codeはコマンド文字列をサブコマンドに分解し、env前置きやtimeout等のラッパーを剥いだ変異形を作ってパターン照合するが、**env代入の値に`$`があると剥がせない**（値の文字クラスが`$`を除外している。claude 2.1.226のマッチャ実装で確認）。`CLAUDE_CODE_SESSION_ID=$SID ~/…/ensure-codex.sh …`は除外されずsandbox内で走り、codexが自分のseatbeltを張れずに死ぬ。セッションUUIDはリテラルで書く。`spawn.sh`は`--team`明示ならenv前置き不要（env varは`--team`省略時のデフォルト解決にしか使われない）。1ノードでも一致すると**そのBashリクエスト全体**がsandbox外へ出るため、`;`/`&&`/パイプでの併記は道連れになる。forループやコマンド置換の中では逆にマッチ自体が壊れる
11. **headless claude-code worker(fable-review等)の認証はsetup-tokenの長命トークンで固定している**: worker専用の`CLAUDE_CONFIG_DIR`(`~/.agents/skills/agmsg/db/claude-worker-home`)の`settings.json`に`env.CLAUDE_CODE_OAUTH_TOKEN`(`claude setup-token`発行の1年トークン、2026-08-11導入・mode 600)を置いてある。公式の認証優先順位でenvトークンは`/login`の保存ログインより上位なので、保存ログインの期限切れはworkerに影響しない（spawnが渡す`--settings`もuser settingsの`env`を潰さない）。**preflightは`CLAUDE_CONFIG_DIR=$HOME/.agents/skills/agmsg/db/claude-worker-home claude auth status --json`** で、`authMethod`が`oauth_token`なら正常。認証が失われると`-p`は`401 OAuth access token is invalid`で即死し、spawnからは`Claude reviewer sandbox probe did not produce every required correlated tool event after 2 attempts (last rc=1); refusing fail-closed`のようにprobe失敗として見えるため、sandbox由来と誤読しない（未認証workerはtool eventを出せない）。復旧は`claude setup-token`を再発行して同キーを差し替える。config dirは全workspace共通なのでcwdは無関係で、workspaceごとのログインは不要。codexワーカーは別系統なので影響しない
12. **同一workerのbridgeが2重に生きていることがある**（`despawn.sh --force` → `ensure-codex.sh` の入れ替え時に発生しうる）。二重処理・返信重複を招くので `pgrep -laf codex-bridge` でworker名ごとの本数を確認し、重複していたら `despawn.sh <team> claude <worker> --force` で一旦全部落としてから1本だけ立て直す
13. **cursorの`model label mismatch`でdead-letterされる**: `init.model`の表示はカタログ名と一致しないことがあり、同一`--model` idでもチャットごとに別ラベルが返る(2026-08-21: `claude-opus-5-thinking-max` が `Claude Opus 5 1M Max Thinking` と `Claude Opus 5 300K Max` を交互に返した)。configの1ラベル追従では追いつかない。`spawn.cursor_model_label.<name>` に観測した表示を `|` で列挙し、**bridgeをdespawn→再spawn**する(configは起動時argvに焼き込まれる)。片方だけのpin更新では逆方向のmismatchが起きる
14. **claude-code workerのprobe失敗は`rc`で2原因に切り分ける**(2026-08-29実測): `Claude <layout> sandbox probe did not produce every required correlated tool event after 2 attempts (last rc=N)` は**同一文言で別原因**が出る。`rc=124`ならprobe timeout(この項)、`rc=1`ならworker homeの認証切れ(項11)。rcを見ずにsandbox由来と誤読しない。probe timeoutの既定は30秒(`drivers/types/claude-code/_spawn.sh`の`AGMSG_CLAUDE_PROBE_TIMEOUT:-30`)で、fable-reviewは30秒ではtool eventを出し切れない。`AGMSG_CLAUDE_PROBE_TIMEOUT=150`を前置きして起動する(per-nameのconfigキーは無くenv varのみ。値はリテラルで書く — 項10)。失敗した2回分のprompt/trace/stderr/settingsを残すには`AGMSG_CLAUDE_KEEP_PROBE=1`を併せて付ける(パスがstderrに出る)。**`ensure-headless.sh`はspawn.shの出力を`>/dev/null 2>&1`で捨てる**ため、原因は`ensure-...: failed to spawn ... — run spawn.sh directly to see why`としか出ない。直接再実行する形は `spawn.sh claude-code fable-review --team <team> --project <path> --headless` — **語順が`ensure-headless.sh <type> <project> [name]`と違い**(`spawn.sh <type> <name> [options]`)、`<project>`を第2引数に置くと`spawn: unknown option: <name>`になる。**`--headless`を落とすとreviewer layoutにならない**
    - **同じ`failed to spawn`は`ensure-codex.sh`(codex系)でも起きる**。`ensure-codex.sh <project> <name>` が `failed to spawn ... — run spawn.sh directly to see why` で終わったら、同様に `spawn.sh codex <name> --project <path> --team <team> --headless` へ置き換える。語順の違い(`ensure-*`は`<type> <project> <name>`、`spawn.sh`は`<type> <name> --project`)は項14前段と同じ罠。
    - 補助スクリプトの引数: `history.sh <team> [agent_id] [limit]`(第1引数はteam名。project pathを渡すと `invalid team name ... path traversal` になる)。**`team.sh list` は存在しない** — 登録一覧は `identities.sh <project_path> <agent_type>` で見る。`whoami.sh <project_path> [type]`。
    - 実例: 2026-09-06、この項を読まずに試行錯誤して4回失敗した(`ensure-codex.sh`の失敗 → `spawn.sh`に project を第2引数で渡して `unknown option` → `team.sh list` で `Team not found` → `send.sh` に project path を渡して path traversal エラー)。**`ensure-*`が失敗したらまずこの項を読む。**
